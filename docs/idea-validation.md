# 想法验证：跨模型自动上下文压缩

## 一句话

让 DSH 在对话快塞满前，自动把较早的历史整理为一份可继续工作的摘要，并保留最近的对话；如果模型已经卡在一条长时间的思考中，也要能安全地恢复，而不是无限等待。

## 给谁用 / 解决什么

- **给谁用**：使用 DSH 做长时间开发、研究或多轮协作的个人开发者。
- **核心问题**：用户切换到 ChatGPT 后，历史对话接近容量上限，当前回复长时间停在思考中。用户无法判断系统是在工作、已超限，还是已经卡死。
- **关键假设**：自动压缩应是 DSH 的通用能力，不能只针对某一个模型或塞进账号绑定插件。

## 已核验的现状

DSH 当前版本并非完全没有自动压缩：

- 标准模式和“虚拟产品团队”模式都已装载 `dsh-compaction-basic`；
- 默认会在每个工作步骤开始前，于已使用约 **80%** 容量时压缩早期历史；
- ChatGPT 的 GPT-5.6 Terra/Luna/Sol 路由已声明 **272,000** 的对话容量；
- 系统还会在模型明确返回“容量超限”错误时压缩并重试一次；
- 用户也可在回复结束、系统空闲后输入 `/compact` 手动触发。

### 初步缺口

现有机制只在“下一步工作开始前”或“模型明确报出超限”时介入。若模型在同一条正在执行的长回复中持续思考、且没有返回可识别的超限错误，自动压缩不会抢占这次执行。因此，修复重点不是从零重复造压缩功能，而是补齐“长时间无进展时的识别、停止、压缩与继续”的恢复链路，并让用户看得见发生了什么。

## 调研结论

- **市场与竞品**：长对话自动压缩是成熟的智能助手能力；OpenAI 和 Claude Code 都公开讨论了会话记忆/上下文压缩。用户的痛点真实且符合行业做法。
- **可行性**：DSH 已有容量统计、摘要生成、历史替换、超限恢复和手动命令，技术基础完备。新增恢复链路的范围可控。
- **MVP 初判**：
  1. 保留现有的 80% 提前压缩；
  2. 为“长时间没有有效输出”的请求增加可配置的看护与一次安全恢复；
  3. 恢复前保存原历史，压缩失败则停止并明确说明，不重复无限尝试；
  4. 在界面中显示“正在整理历史/已恢复/需要你重试”，而不是静默卡住。

## 范围扩展（用户补充）

用户进一步指出：问题可能覆盖整个模型执行过程，而非单独的上下文。

- 通过 DeepSeek 官方 API：上下文注入、思考、工具调用、任务清单、提问与命令执行正常且快；
- 通过 OpenCode Go 订阅使用 DeepSeek：可能出现思考被当作正文、速度明显变慢、思考结束后任务中断；
- 千问等模型未复现同类表现。

因此，正在把验证范围扩大为“跨模型运行可靠性”：分别核验模型/网关协议、DSH 适配层、会话执行循环、界面渲染、工具调用和恢复机制。目标是判断一个独立的运行看护插件可以安全处理哪些问题，以及哪些必须由 DSH 核心修补。

## 裁决

**⚠️ 调整后做。**

值得做，但目标应精确改为：**建立跨模型的运行可靠性与诊断能力：既修补 DSH 已有自动压缩在长时间思考场景下不能及时接管的缺口，也识别和处理第三方路由造成的思考流、工具调用、任务中断和死亡循环问题。**

## 证据

- DSH 本机 `dsh-compaction-basic`：默认阈值 80%，已支持自动压缩、超限恢复与摘要替换。
- DSH 本机 `dsh-command-compact`：已提供空闲时的 `/compact` 手动兜底。
- [OpenAI：长运行智能助手的上下文整理](https://developers.openai.com/cookbook/examples/agents_sdk/building_reliable_agents_memory_compaction)
- [Claude Code：上下文窗口与自动压缩](https://code.claude.com/docs/en/context-window)
- [OpenCode 社区：DeepSeek thinking 模式的 `reasoning_content` 在工具调用续接时丢失会导致中断](https://github.com/anomalyco/opencode/issues/35689)
- [OpenCode 社区：DeepSeek V4 的 reasoning 内容未回传导致多轮工具调用失败](https://github.com/anomalyco/opencode/issues/24190)

## 初步证据：OpenCode Go 的 DeepSeek 兼容链

DSH 本机的 OpenCode Go DeepSeek V4 路由走 OpenAI 兼容的聊天接口，声明了 `thinkingFormat: "deepseek"` 与“后续请求必须回传 `reasoning_content`”的专门兼容规则。DSH 当前底层适配器也针对 `opencode-go` 的 `reasoning` 字段做了转换；这说明问题并非用户误操作，而是该类网关/模型组合确实有不同于 DeepSeek 官方 API 的协议要求。

此外，该路由对外声明 100 万 token 容量，因此 DSH 默认 80% 的预防性压缩要到约 80 万 token 才会触发；这会让“虽然很长、但尚未到 80 万”的会话缺少提前整理。这是可配置策略缺口，不是自动压缩完全不存在。

但仍不能据此断定本次问题已被本机版本完全修复：需要采集一次去敏后的请求生命周期，确认实际收到的流式字段是 `content`、`reasoning` 还是 `reasoning_content`，以及中断时的结束原因/错误码。

## 运行可靠性审计

已确认 DSH 已具备“单次流 300 秒无数据超时、取消信号、可持久化的请求重试、上下文压缩”。但它没有统一判断“任务是否真的在推进”的运行监督机制，也没有对步骤数、总耗时、连续失败、重复工具调用或预算设置跨模型的硬上限。

这带来明确的两层交付边界：

1. **独立插件可交付**：去敏运行记录、当前步骤/流类型/错误码看板、每条路由的压缩阈值建议、异常预警、有限次数的安全重试与用户可见恢复建议。
2. **DSH 核心必须配合**：强制终止不响应的流或工具、在异常中保持工具调用/结果配对、原子恢复、不可绕过的循环/总时限/预算限制。

## Gate 1 裁决

**✅ 值得做，采用“双层方案”。**

先做一个可分发的“模型运行守护”插件，解决看不见、诊断不了、不能安全重试和不能按路由调策略的问题；同时为 DSH 核心整理一份必须补齐的可靠性改动清单。插件不承诺掩盖第三方网关的协议错误，而是准确发现、停止扩大损失、保留去敏证据并给出恢复路径。

### 初版验收

- 至少覆盖 DeepSeek 官方、ChatGPT/Codex、OpenCode Go DeepSeek、千问四类路由的诊断；
- 明确区分思考流、正文流、工具调用、工具结果、超时、上下文超限与空回复；
- 面对同一异常最多做一次自动恢复，绝不无限重试；
- 不记录对话正文、工具输出、认证信息或模型私有思考内容；
- 为无容量或协议不规范的路由明确显示“不能安全自动修复”的原因；
- 将不可由插件可靠解决的问题生成可复现、去敏的 DSH 核心修复报告。

## GitHub / 上游问题梳理补充

已核验到与本次现象直接相关的公开问题与修复方向：

- pi 仓库已记录 OpenCode Zen 网关在 DeepSeek reasoning 回放上的故障，并有对应兼容修复 PR；
- OpenCode 仓库已有 DeepSeek V4 Pro 经 `zen/go` 时 `reasoning_content` 不一致的问题报告；
- 这些记录与本机的协议路径、DSH/pi-ai 现有补丁和用户症状一致，说明这不是孤立个案。

因此，插件除了解决“看不见、诊断不了、不能安全重试”之外，还应内置一份**已知第三方兼容问题清单**：当检测到匹配特征时，直接给出“这是某网关已知问题 + 当前可用规避方式 + 是否已由上游修复”的结论，而不是让用户反复试错。
